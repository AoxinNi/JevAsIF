# 差异化定位：本体中介的程序化工具调用

> 日期：2026-09-23　｜　承接 [01-方向调研报告](01-方向调研报告.md)

## 0. 结论

不要和 Programmatic Tool Calling（PTC）正面竞争，而是**把它吸收进来**：Agent 仍然写程序、一次执行，但程序调用的是**本体编译出来的类型化接口**，而不是裸工具。本体同时承担三件 PTC 不做的事：

1. **让模型会用自定义工具**：给出类型化的出参、跨工具的依赖、业务规则，并在执行前做静态检查。
2. **做安全边界**：执行点在计划语言之下，身份、范围、溯源的策略由本体声明推导出来。
3. **免训练的场景适配**：改本体就能提升 Agent 在某个场景的表现，不微调模型。

Jev / System-1 从核心降为增强组件：作为程序里的 `decide()` 原语，处理运行期的模糊判断。这样课题不再依赖一个闭源 API 能否拿到、好不好用。

## 1. Claude 能熟练编排自定义工具吗？

**会写代码不等于会用你的工具。** 对自定义工具，PTC 的瓶颈不在代码语法，而在三类信息缺失：

| 缺什么 | 后果 | 佐证 |
| --- | --- | --- |
| **出参结构**：MCP 工具通常只声明入参，出参字段名、嵌套层级、枚举含义不明 | 代码只能猜字段名，或先 `print` 出来看一眼再写下一段，一次执行又退化成多轮 | Anthropic 自己推出 Tool Use Examples，理由是"合法的 JSON 不等于正确用法"；内部测试中，复杂参数处理的准确率从 72% 提到 90% |
| **跨工具依赖**：哪个工具的哪个输出，是哪个工具的哪个输入（如 `read_fees.chargeNumber` 必须来自 `read_basic`） | 调用顺序错、参数来源错 | In-N-Out：参数级依赖图让多工具查询生成的表现接近翻倍；ToolHop 上 GPT-4o 只有 49% |
| **业务规则**：先查范围、按客户授权、哪些数据是演示数据、哪些话不能说 | 程序能跑通，但业务上是错的，或者越权 | 这些规则通用模型无从得知，只能靠提示词，而提示词无法强制执行 |

PTC 的收益本身是真实的：官方数字是复杂研究任务上平均 token 从 43,588 降到 27,297（-37%），20 多个工具调用写在一个代码块里就省掉了 19 次以上的推理往返。但这个数字来自 Anthropic 自选的任务，**没有回答"陌生的领域工具"这个问题**，而这正好是你可以用实验回答的。

**本体能补上这三类信息：**

- **出参结构**：对象、属性、类型，外加工具注册表的 `fields` 映射，可以编译成带出参类型的接口桩（typed stub）。
- **跨工具依赖**：`input` / `output` 属性，加上 `traced` 规则，就是现成的参数级依赖图。
- **业务规则**：语义帧里的规则，由运行时强制执行。

→ **差异点 1：本体是 Agent 编排自定义工具的"类型化标准库"，并且带编译期检查。** 计划或程序在执行任何工具之前先过一遍检查：类型对不对、依赖是否满足、是否先查了范围。错误以结构化信息返回给模型修正。这比"执行失败后再返回"便宜，也更安全。

## 2. 安全能不能做卖点？能，但要讲准"隔离了什么"

### 2.1 PTC 隔离的是计算，不是业务权限

PTC 的沙箱防的是代码对宿主环境的破坏。但在沙箱里：

- 允许调用的工具，代码可以用**任意参数**调用；
- 客户号这类身份参数如果是工具入参，模型就能改；
- 工具返回的不可信数据进入代码之后，可以左右后续的分支和参数。

这些都要靠开发者在工具侧自己把关。

### 2.2 你的本体做的是业务权限隔离

项目里已经实现了这些机制：

| 机制 | 效果 |
| --- | --- |
| 身份注入（`fill: identity`） | Agent 的参数契约里根本没有客户号，想越权也写不出来 |
| 范围复核（`check: scope`） | 每次调用前重新获取客户可咨询范围，缓存不算授权 |
| 入参溯源（`check: traced`） | 下游参数必须是本运行真实返回过的值，杜绝编造 |
| 模式约束 | 对象模式只执行只读工具；外部审批事件 Agent 不能代答 |
| 工具细节不出服务端 | 接口地址、凭据、宿主上下文，Agent 和本体都看不到 |

**关键性质：这些检查在计划语言之下。** 无论 Agent 提交的是 JSON 调用、批量 steps 还是一段代码，只要最终经过同一个本体网关，检查就同样生效。

### 2.3 与安全文献的差别

| 工作 | 做法 | 你的差异 |
| --- | --- | --- |
| CaMeL | 自定义解释器、能力标签，**每个工具的策略手写** | 策略**由业务本体的声明推导**（`fill` / `check`），业务人员维护本体时顺带维护了策略 |
| Progent | 工具级权限 DSL，由 LLM 按用户请求生成策略 | 权限来自可信的业务定义，而不是模型生成的；另有值级溯源 |
| ActGov | LLM 只做有界抽取，输出布尔或类别值 | 与 System-1 选择式绑定同一思路，可互相引用 |

### 2.4 一个可以升级的研究点

现在的溯源是**按值比较**：提交的值只要等于本运行里观测到的某个值就放行。如果别处恰好有相同的值（例如 `chargeNumber=1`），就可能被"借用"。编译式计划天然给出更强的形式：**绑定是引用（`s2.records[0].chargeNumber`），不是值**，溯源由结构保证。这可以作为论文里的一个技术点：**编译期引用把溯源从值级检查变成结构性保证。**

→ **差异点 2：策略从本体推导，并在计划语言之下强制执行。** 建议作为第二贡献，不作为唯一主线。单做安全要和 CaMeL、Progent 在 AgentDojo 上正面比，需要严格的威胁模型。

**评测：**

- AgentDojo（NeurIPS 2024，97 个任务、629 个安全用例）；
- 自建证券场景威胁集：越权查询其他客户（IDOR）、篡改参数、工具返回的产品文案里藏注入、编造事实。

指标：攻击成功率，以及加防御后还剩多少任务成功率。

## 3. 免训练的场景提升：成立，而且贴近落地

主流的"让 Agent 在某个场景变强"靠训练：

- ToolLLM 类指令微调；
- GAP 用强化学习；
- TinyAgent 微调小模型；
- In-N-Out 微调模型来生成依赖图。

你的做法是**改本体，不改模型**。项目已经具备的配套：

- 业务人员在工作台编辑本体，发布后热替换；
- 版本按指纹固定，已开的运行继续用原版本；
- `disclosure.hops` 控制开局视野。

→ **差异点 3：本体是免训练的场景适配器，由业务人员维护。**

**要预先回答审稿人的质疑："这不就是写了更好的文档吗？"** 需要一组消融，把收益拆开：

| 条件 | 说明 |
| --- | --- |
| 裸工具 schema | 基线 |
| 裸 schema 加 Tool Use Examples 式示例 | 业界已有的免训练做法 |
| 本体渲染成纯文本文档塞进提示词 | 只有"文档"的收益 |
| 本体加编译期检查与修复 | 文档之外的收益，来自类型和依赖检查 |
| 本体加编译加运行时网关 | 完整方法 |

**还必须报告本体的编写成本**：人时、字段数。同时要和 OaK 区分：OaK 是自动构建本体，服务于知识与推理；你的本体是执行契约和安全边界，服务于编排与执行。

## 4. 统一定位

### 4.1 架构

```text
Agent（大模型）
  │ 写程序：Python 子集或 JSON IR，调用的是本体编译出的类型化接口，而不是裸工具
  ▼
编译器 ── 静态检查：类型 / 依赖 / 入口先行 / 规则 ──→ 不通过：结构化错误交回 Agent 修正（此时尚未执行任何工具）
  │ 通过
  ▼
运行时（本体网关）── 每次调用：身份注入、范围复核、引用溯源、只读约束、审计
  │ 模糊判断 → decide() 原语：System-1（Jev / 开源替代），置信门控，不够就回退大模型
  ▼
最终结果 → Agent 作答
```

### 4.2 对比表

| | ReAct | LLMCompiler | PTC / CodeAct | CaMeL | Progent | 微调类 | **本课题** |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 一次执行串行链 | ✗ | 部分（直接引用） | ✓ | ✓ | — | — | ✓ |
| 懂自定义工具的出参和依赖 | 靠读文档 | 靠读文档 | 靠读文档或先打印 | 靠读文档 | — | 靠训练 | **本体提供，编译期检查** |
| 运行期模糊判断 | 大模型 | 重规划 | 代码硬匹配或再调大模型 | 隔离 LLM | — | — | **System-1 加置信门** |
| 业务权限强制 | ✗ | ✗ | 靠开发者 | 手写策略 | DSL 或 LLM 生成策略 | ✗ | **由本体推导** |
| 免训练 | ✓ | ✓ | ✓ | ✓ | ✓ | ✗ | ✓（改本体即可） |

### 4.3 可选题目

- *Ontology-Mediated Programmatic Tool Calling: Typed, Policy-Enforced, One-Shot Tool Orchestration without Training*
- 中文：本体中介的程序化工具编排——免训练、可验证、一次执行

### 4.4 贡献排序建议

1. **主贡献**：本体编译成类型化接口，加上编译期检查，提升陌生领域工具的一次执行成功率（准、快、省）。
2. **第二贡献**：由本体推导策略，在计划语言之下强制执行；编译期引用让溯源成为结构性保证（安全）。
3. **增强组件**：System-1 的 `decide()` 原语加置信门控，覆盖运行期的模糊判断。

## 5. 下一步：小规模先导实验（1–2 周）

在 v04 组合详解本体上，同一个模型（先用项目里已配好的 DeepSeek，论文里加 Claude 等多个模型），对同一组问题比较：

1. **ReAct**：现在的真实 Agent 模式；
2. **PTC 式**：给裸工具 schema，模型写一段 Python 一次调完；
3. **PTC 式加本体**：给本体编译出的类型化接口桩和规则，模型写 Python；
4. **第 3 种加编译期检查**。

记录：
- 一次写对的比例；
- 为查看出参而多出的往返次数；
- token 数与延迟；
- 越权或编造被网关拦下的次数。

如果第 2 种在"一次写对"上明显差于第 3、4 种，差异点 1 就有了第一份证据。
