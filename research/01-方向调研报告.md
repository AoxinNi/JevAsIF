# 本体驱动的工具编译器：System-1 模型做运行期参数绑定——方向调研报告

> 日期：2026-09-23　｜　性质：研究方向调研（lit-review + 研究设计草案）　｜　依托项目：`DEMO-V8-最小运行包`（本体 + MCP 运行时）

---

## 0. 一页结论

1. **方向成立，但要换一个说法。** Jev 不能"填任意参数"。它只回答三类问题：从最多 255 个选项里选一个（Choice），按等级打分（Score），给是否题一个概率（Noul）。数字、日期、自由文本它都不生成，官方示例里这类参数直接保留函数默认值。所以更准确的说法是：**串行工具链里，凡是依赖上游结果、需要"看结果再判断"的参数，在运行期把上游结果变成候选集，交给 System-1 模型去选。** 这可以叫"System-1 延迟绑定"（late binding）。
2. **真正的空白不在"一次执行"，而在"一次执行时谁来做观测依赖的判断"。** ReWOO、LLMCompiler 已经用 `#E1`、`$1` 这类变量把上游输出直接代入下游参数，能一次执行"直接引用"型依赖。它们处理不了的是另一类：规划时不知道上游会返回什么，而下游参数取决于"返回了什么"。例如从返回的 12 个组合里挑出名字对应"目标盈"的那个，或者按返回的产品类型决定走哪条分支。这时它们只能回到大模型重规划（replan），等于退化成 ReAct。现有文献里，没有工作用校准过的非生成式小模型专门处理这类运行期判断，并用置信度决定"继续执行 / 回退大模型"。
3. **你的项目天然适合这个课题，有三个现成条件：**
   - 对象本体里每个操作声明了 `input` / `output` 属性，入参溯源（`check: traced`）已经在运行时强制执行。这本身就是一张**参数级数据流图**，而这正是 In-N-Out（TACL 2026）花大力气人工标注的东西。
   - 操作模式引擎已经有 `selection` 任务节点（带 `options`，答复为选中值），和 Jev 的 Choice 一一对应。
   - 对象模式的 execute 已支持 `{steps:[…]}` 批量只读调用，相当于"没有依赖的 LLMCompiler"。编译器只需在它上面加依赖和绑定。
4. **最大的风险有三个：**
   - Jev 是闭源早期访问产品，没有论文，性能数字都是厂商自报，学术上难以复现；
   - 官方文档说明中文等 CJK 语言准确率偏低，而你的场景是中文证券业务；
   - 最强的对手不是 LLMCompiler，而是"让 LLM 写代码一次调完所有工具"（CodeAct、Anthropic Programmatic Tool Calling）。

   建议把 System-1 做成**可替换的判断后端接口**：Jev 是其中一个实现，另配一个开源实现（小模型或重排序模型加约束解码）。这样论文不依赖某个商业 API，也能证明收益来自架构，而不是某个模型。

## 1. 背景：项目现状与问题

### 1.1 项目里已经有什么

| 能力 | 在项目中的体现 | 对编译器的意义 |
| --- | --- | --- |
| 对象本体（`executionMode: object`） | 给 Agent 提供对象、关系、操作契约、规则；Agent 自己决定调用顺序 | 编译器的**类型系统和静态检查依据** |
| 操作本体（`executionMode: operation`） | 流程图，引擎自己推进；只在 `selection` / `generation` / `event` 节点交出任务 | 编译器的**执行后端**（IR 可以直接编译成一份临时操作本体） |
| 工具注册表 | 参数的 `fill`（identity/host/agent/const）、`check`（scope/traced） | 编译器知道哪些参数由系统注入、哪些要溯源、哪些要复核范围 |
| 入参溯源 `FACT_NOT_OBSERVED` | 下游参数必须等于本运行真实返回过的值 | 从上游结果里**选**出的值自动满足溯源，这是"选择式绑定"的天然安全性 |
| 批量只读 `{steps:[…]}` | 一次提交多个互不依赖的只读操作 | 已经实现了无依赖的并行，下一步是有依赖的串行 |
| 渐进披露 `disclosure.hops` | 控制 Agent 开局看多远，决定走 query 扩展（A）还是直接调用（B） | 编译器规划前需要多大视野，本身就是一个实验变量 |

### 1.2 现状的代价

以已有实测为例（v04 组合详解，问"zhbtest001 的费用怎么收"）：hops=1 时 Agent 走 `read_scope → query(FeeSchedule) → read_basic → read_fees`，共 4 次工具往返，每次都要一轮大模型推理，总计约 25.4k token。其中 `read_fees` 的参数 `chargeNumber` 必须等 `read_basic` 返回后才知道。这就是典型的**参数依赖串行链**：ReAct 每一步都得让大模型重读全部上下文再决定下一步。

## 2. Jev / System One 模型：能做什么、不能做什么

资料来源：TypeSafe 官方博客与文档（厂商灰色文献，未经同行评审）。

| 维度 | 事实 |
| --- | --- |
| 定位 | "System One Model"：面向自动化的快速结构化决策，不做对话、不生成文本、不写代码 |
| 输入 | `state`：字符串、JSON 对象或数组，只支持文本 |
| 输出 | 三类问题：**Choice**（从选项中选一个，附每个选项的概率和置信度，**最多 255 个选项**）、**Score**（按描述性等级打分）、**Noul**（是否题，返回 0–1 的概率） |
| 并行 | 一次请求可带很多问题，所有问题基于同一份 state 独立评估；官方提倡"speculative fan-out"，把可能用到的问题一次都问了，由代码决定用哪个 |
| 速度 / 成本（厂商自报） | 端到端 70–500ms；输入 $0.042 / 百万 token，输出免费；工作流评测号称"193.6 倍更快、444.6 倍更便宜"（厂商自称属于"真实收益的高端"） |
| 训练 | RLCD（Reinforcement Learning for Calibrated Decisions），强调**概率校准** |
| 函数调用 | 官方有 function calling cookbook：函数名做一个 Choice，`Literal` 参数做 Choice，`bool` 做 Noul，`list[Literal]` 拆成每个成员一个 Noul。**int、自由文本、日期不出问题，沿用函数默认值** |
| 局限 | 只支持文本；**CJK 语言可用但准确率较低**；选项上限 255（更多需分两级）；闭源，早期访问 |

**对课题的含义：**

- Jev 适合做的是**选择式绑定**：候选值在运行期从上游工具结果中产生，比如"返回的 N 条记录里选哪条""返回值落在哪个枚举""下一步走哪条分支"。它**不适合**做数值计算、字符串拼接、日期推算这类**变换式绑定**，这些应交给确定性代码。
- 它的置信度是训练目标的一部分，所以可以设计"置信度门控"：高于阈值就继续执行，低于阈值就回退给大模型或向客户澄清。这是"准"的来源。
- 它的"快"和"省"建立在**把大模型从执行循环里拿掉**上，而不是让大模型本身变快。

## 3. 相关工作

证据等级：**T1** 同行评审会议或期刊；**T2** arXiv 预印本；**T3** 厂商或工程博客。所有条目都已联网核实存在。

### 3.1 规划与执行分离、一次编排

| 工作 | 等级 | 核心做法 | 与本课题的关系 |
| --- | --- | --- | --- |
| **ReWOO**（arXiv 2305.18323, 2023） | T2 | Planner 一次写出带 `#E` 变量的完整计划，Worker 执行，Solver 汇总；HotpotQA 上 token 效率约 5 倍 | 最早的"先规划、后执行、变量代入"。**依赖只能直接代入，观测依赖的判断无法在执行期完成** |
| **LLMCompiler**（Kim et al., ICML 2024） | T1 | Planner 生成带依赖的任务 DAG，任务获取单元调度，执行器并行执行；相比 ReAct，延迟最多降 3.7 倍，成本最多降 6.7 倍，准确率最多升约 9% | 主要优化**并行**。串行依赖靠 `$id` 代入；需要看结果再判断时走 replan，回到大模型 |
| **LLM-Tool Compiler**（arXiv 2405.17438, 2024） | T2 | 把相似工具操作融合成一个函数，提高并行调用率；token 最多降 40%，延迟最多降 12% | 同属"编译器"思路，但只做融合与并行 |
| **Chain-of-Abstraction**（arXiv 2401.17464, 2024） | T2 | 微调 LLM 先生成带占位符（y1、y2…）的抽象推理链，再由工具填充；解码与工具调用可并行 | "占位符 + 延迟填充"与本课题同构，但由工具直接填，没有运行期判断 |
| **Plan-and-Act**（arXiv 2503.09572, 2025）；**Secure Plan-then-Execute 指南**（arXiv 2509.08646, 2025） | T2 | 规划与执行分离，后者从架构上讨论可预测性、成本与安全 | 设计模式层面的佐证 |
| **Reverse Chain**（NAACL 2024 Findings, arXiv 2310.04474） | T1 | 目标驱动的反向链：先选最终 API，缺参数再选能产出它的 API；把 LLM 限制在"选 API、补参数"两个简单任务上 | 与"本体声明谁产出哪个属性、反向推出调用链"高度一致，可作为**规划算法**的对照 |
| **GAP**（arXiv 2510.25320, 2025） | T2 | 用 RL 训练模型输出依赖感知的子任务图，自适应并行和串行执行 | 最新的"依赖图规划"训练路线，属于规划侧 |

### 3.2 代码即动作：最强的竞争路线

| 工作 | 等级 | 要点 |
| --- | --- | --- |
| **CodeAct**（Wang et al., ICML 2024） | T1 | 用可执行 Python 统一动作空间，一段代码里可串联多个工具调用；成功率最多高 20% |
| **Anthropic Programmatic Tool Calling / Code execution with MCP**（2025） | T3 | 模型写代码在沙箱里调 MCP 工具，中间结果不进上下文；官方案例 token 从 15 万降到 2 千（-98.7%） |
| **AppWorld**（ACL 2024 最佳资源论文） | T1 | 9 个 App、457 个 API，任务需要交互式写代码调用 API；是评测代码式 Agent 的难基准 |

**为什么它们是主要对手：** 写代码一次调完，同样能"一次执行串行链"，而且确定性变换（加减、拼接、过滤）用代码最自然。**但是**代码里一旦遇到模糊判断（"哪条记录是客户说的那个组合"），要么硬编码字符串匹配（脆弱），要么在代码里再调大模型（又慢又贵），要么停下来回到大模型（回到多轮）。本课题的差异化就在这里：**模糊判断由校准过的 System-1 完成，并由置信度控制是否回退；程序结构受本体类型约束，可以静态检查、审计，并执行权限复核。**

### 3.5 安全：选择式绑定的附带收益

| 工作 | 等级 | 要点 |
| --- | --- | --- |

## 4. 研究空白

1. **绑定类型没人统计过。** 现有工作把"参数依赖"当成一种东西。实际上，下游参数怎么从上游得到，至少有五类：
   - **常量**：规划时已知；
   - **直接引用**：取上游某个字段，可用 JSONPath 表示；
   - **选择**：从上游返回的多个值里按语义挑一个；
   - **变换**：确定性计算；
   - **生成**：需要自由文本。

   ReWOO 和 LLMCompiler 只覆盖前两类，第三类一出现就重规划。**没有工作量化过真实任务中各类占比。**这本身就是一个可发表的实证发现。
2. **执行期的模糊判断缺一个又快、又便宜、又校准的执行者。** 目前的选项只有三种：大模型重规划（慢、贵）、代码硬匹配（脆弱）、不处理（出错）。
3. **一次执行缺少带统计保证的回退机制。** 一次执行的错误会沿依赖链累积，现有编译式方法没有"什么时候该停"的量化准则。
4. **本体或类型系统没有用在工具编排的"编译期"。** 工具的类型和依赖通常靠 LLM 读文档推断，而不是编译器静态检查。

## 5. 候选研究问题

- **RQ1（实证）**：在嵌套和多跳工具调用基准，以及真实证券业务场景中，参数依赖的五类绑定各占多大比例？其中"选择型"依赖是不是 ReWOO 和 LLMCompiler 失败或重规划的主要来源？
- **RQ2（方法）**：计划 IR 由本体类型约束，选择节点由 System-1 在执行期绑定，整条链一次编译执行。相比 ReAct、ReWOO、LLMCompiler、CodeAct（Programmatic Tool Calling），它在**延迟、成本、准确率**三个维度上能否达到更优的帕累托前沿？
- **RQ3（可靠性）**：以 System-1 置信度为分数、用共形预测标定阈值的门控，能否把一次执行的绑定错误率控制在给定的 α 以下？回退率是多少？
- **RQ4（可选，安全）**："本体类型约束 + 选择式绑定 + 入参溯源"对间接提示注入的鲁棒性如何？

一个可操作的论文题目方向：*Ontology-Typed Tool Compilation with System-1 Late Binding: Executing Dependent Tool Chains in One Shot*。

## 6. 方法设计草案

### 6.1 整体流程

```text
客户请求
  │
  ▼
[大模型 Planner]  读取对象本体语义帧（hops 决定视野）
  │  产出：计划 IR（类型化的调用 DAG + 绑定声明）
  ▼
[编译器]
  ① 类型检查：参数类型、所属对象、fill/check 规则都要符合本体和工具注册表
  ② 依赖分析：由 output→input 属性生成参数级 DAG；检查入口先行、范围复核
  ③ 绑定分类：const / ref / choice / transform / gen
  ④ 调度：无依赖的并行（沿用 LLMCompiler），choice 问题投机式一次问完（Jev fan-out）
  ⑤ 插入守卫：前置条件改成 Noul 检查；每个 choice 设置置信门
  ⑥ 生成可执行形式：一份临时操作本体（节点 = action / selection / guard / end）
  ▼
[执行引擎：复用操作模式运行时]
  action 节点 → 调工具；selection 节点 → System-1 回答；transform → 确定性函数
  置信度 < τ 或守卫失败 → 带部分轨迹和具体问题，回退大模型（一次）或向客户澄清
  ▼
[大模型 Answerer]  基于最终结果生成中文回答（可与 Planner 合并为同一模型的第二次调用）
```

最理想的调用次数：**大模型 2 次（规划 + 作答），System-1 若干次（毫秒级），工具若干次**。ReAct 的大模型调用次数则等于工具调用次数加 1。

### 6.2 计划 IR 示例（v04 费用问题）

```json
{
  "steps": [
    {"id": "s1", "action": "read_scope", "parameters": {}},
    {"id": "s2", "action": "read_basic",
     "parameters": {"combineCode": {"choice": {
        "from": "s1.records[*].combineCode",
        "label": "s1.records[*].combineName",
        "question": "客户询问的是哪一个组合？",
        "state": ["$user_utterance"], "tau": 0.8}}}},
    {"id": "s3", "action": "read_fees",
     "parameters": {"chargeNumber": {"ref": "s2.records[0].chargeNumber"}}}
  ],
  "answer": {"use": ["s2", "s3"]}
}
```

- `s2.combineCode` 是**选择型**：规划时不知道客户可咨询范围里有哪些组合，只能在运行期从 `s1` 的结果里选；选出的值自动满足入参溯源（`traced`）。
- `s3.chargeNumber` 是**直接引用**：不需要任何模型。
- 如果 `s2` 的置信度低于 0.8，编译器停下，带着候选列表回退，只多一次大模型调用，而不是整个 ReAct 链。

### 6.3 与现有项目的映射

| 编译器组件 | 复用或扩展项目中的 |
| --- | --- |
| 类型系统 | 对象本体的对象、属性和操作契约；工具注册表的 `fill` / `check` |
| 依赖图 | 操作的 `input` / `output` 属性，以及入参溯源规则 |
| 执行后端 | 操作模式引擎：节点、分流汇合、遍历、超时、补偿、审计 |
| choice 节点 | 操作模式的 `selection` 任务，答复者从 Agent 换成 System-1 |
| 批量执行 | 对象模式 `{steps:[…]}` 扩展为带依赖和绑定的 steps |
| 披露深度 | `disclosure.hops`：Planner 规划前需要看多远，是一个实验变量 |

### 6.4 System-1 后端接口

```text
decide(state: JSON, questions: [Choice|Score|Noul]) → answers + probabilities + confidence
```

后端实现：
- **Jev**：主实验；
- **开源替代**：例如小参数量 LLM 读取选项的 logprob、交叉编码重排序模型，或微调的分类头，以保证可复现；
- **大模型**：同一接口由大模型实现，作为关键消融，用来分离"架构收益"和"模型收益"。

## 7. 实验设计

### 7.1 基线

1. ReAct（原生函数调用多轮）
2. ReWOO
3. LLMCompiler（含 replan）
4. CodeAct / Programmatic Tool Calling 式代码一次执行
5. **本方法，choice 节点由大模型回答**（消融：只有编译、没有 System-1）
6. **本方法，choice 节点由开源小模型回答**
7. **本方法，Jev**

### 7.2 指标

| 维度 | 指标 |
| --- | --- |
| 准 | 任务成功率；参数（绑定）准确率；最终答案准确率；错误归因（规划错、绑定错、工具错） |
| 快 | 端到端延迟（P50/P95）；关键路径上的大模型调用次数 |
| 省 | 大模型输入与输出 token；按公开价格折算的每任务美元成本 |
| 可靠 | 置信度校准（ECE）；风险-覆盖曲线；给定 α 下的回退率 |
| 安全（可选） | AgentDojo 上的攻击成功率与效用 |

### 7.3 数据

- **公开**：NESTFUL（可执行子集）、ToolHop、NesTools 做主结果；FinMCP-Bench 做中文金融场景；AppWorld 做代码式对手的主场压力测试。
- **自有**：用项目里的证券本体（v04 等）构造一套"参数依赖"场景集，按五类绑定标注，同时回答 RQ1。

### 7.4 关键消融

- 去掉本体类型检查
- 去掉置信门（阈值设为 0）
- hops = 0 / 1 / 2
- choice 候选集规模（10 / 50 / 255 / 超过 255 分两级）
- 中文 state 对比英文字段名加中文值（针对 Jev 的 CJK 短板）

## 8. 风险与反方意见

| 风险 / 质疑 | 严重度 | 应对 |
| --- | --- | --- |
| Jev 闭源、早期访问、没有论文，性能是厂商自报 | **高** | 抽象出 System-1 接口，主要结论也要在开源后端上成立；Jev 的结果作为"上界"或"实用性"补充 |
| Jev 对中文准确率偏低（官方文档明示） | **高** | state 用英文字段名和结构化 JSON，只有值是中文；把中文和英文 state 的对比当作一个实验发现；开源后端选中文能力强的小模型 |
| "选择型依赖"占比可能不高，大多数依赖是直接引用，用 LLMCompiler 的变量代入就够了 | **高** | 这正是 RQ1 要回答的；先做 RQ1 的数据统计，再决定主线。如果占比低，就把主线转向"守卫、分支和置信门控"，即选择型依赖之外的运行期判断 |
| 规划错误占主导：计划错了，一次执行也救不回来 | 中 | 错误归因分析；回退时允许一次局部重规划；hops 实验说明视野与规划质量的关系 |
| 代码式一次执行（Programmatic Tool Calling）已经很强 | 中 | 正面比较；强调差异：类型可检查、权限可复核、可审计，模糊判断有校准；在需要模糊判断的子集上分组报告 |
| 多个 System-1 判断串联，错误会累积 | 中 | 置信门做逐节点的共形标定；报告链长与成功率的关系 |
| 候选集超过 255 | 低 | 两级选择（先粗筛再精选），Jev 文档也推荐这种做法 |
| 业务数据敏感（证券客户） | 中 | 公开实验只用公开基准和合成数据；自有数据脱敏，沿用项目的"合成演示"标注 |

## 9. 建议的推进顺序

1. **先做 RQ1 的数据统计，约 2 周。** 在 NESTFUL、ToolHop 和自有证券场景上标注五类绑定，统计占比，并在 LLMCompiler 上看哪些样本触发了重规划。这一步决定课题值不值得做、主线往哪里偏。
2. **搭最小原型。** 在对象模式 `{steps}` 上加 `ref` / `choice` 两种绑定，choice 先用大模型实现，跑通 v04 费用场景。
3. **接入 System-1 后端。** 先接开源实现，再申请 Jev 早期访问；做中英文 state 对比。
4. **加置信门和共形标定**，跑完整基线对比。
5. **可选**：安全实验（AgentDojo）、hops 与规划质量的实验。

投稿方向：方法与实证偏 NLP，可投 ACL / EMNLP；如果主打延迟、成本和系统设计，MLSys 或系统类会议的 workshop 更合适。
