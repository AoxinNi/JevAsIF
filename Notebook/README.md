# 预实验：Jev-as-IF 完整工作链路

在 FinMCP-Bench 上搭起论文方法的完整链路：**SOG 建图 → MCP 工具服务 → agent 写 PyIF 程序 → 基于图的静态检查 → 执行（工具走 MCP，语义判断走 Jev）→ 作答**，并和 ReAct 基线对比。

## 快速开始

1. 安装依赖（Python ≥ 3.10）。每本 notebook 的第一个代码格也会自动执行这一步：

   ```bash
   pip install -r requirements.txt
   ```

2. 打开 `keys.py`，填入：
   - `TYPESAFE_API_KEY`：Jev 的 key；
   - `LLM_API_KEY`、`LLM_MODEL`：大模型的 key 和模型名，默认地址是 DeepSeek。可以从 ZSZQ 项目的 `api_config.py` 里抄。

   如果设置了同名环境变量，环境变量优先。`keys.py` 已加入 `.gitignore`。

   填完后运行 `python check_keys.py`：它会各发一次最小请求，检查两个 key 是否连通，并列出可用模型，不会打印 key。代码里用 `LLM.from_keys()` 即可拿到配置好的大模型客户端。
3. 在本文件夹里打开 notebook，按编号顺序运行。

## 已验证的情况

所有 notebook 都用本地模拟服务完整跑过一遍，没有报错。模拟服务包括一个模拟 Jev 和一个模拟大模型，后者会按 FinMCP 的标准轨迹回放 ReAct 的调用。**模拟结果没有意义，真实数字要用你的 key 重新跑。** 这些不依赖外部接口的结果是真实的：

- **自动建图**：从 468 条任务归纳出 5 个实体、56 个操作、531 条派生数据流边。派生边对轨迹中实际值流动的召回率是 99.0%，其中从多个候选中选择的流动为 99.6%。
- **回放服务**：多工具子集的 1,827 次标准调用全部回放命中。
- **静态检查**：8 个用例的结果都符合预期（1 个通过，7 个按预期报错）。
- **任务筛选**：多工具子集中有 110 条含语义判断，138 条只有机械依赖。这个筛选比 `finmcp-analysis` 里的启发式更严格：排除了日期、小数、分页参数，以及客户原话里出现过的值，所以含语义判断的任务比之前的 149 条少。

## 已知局限

- **工具参数定义是反推的**：FinMCP 没有提供参数定义，参数描述只有出现次数和取值示例，所有方法都基于同一份定义。拿到且慢 MCP 的正式定义后，替换 `replay.py` 的 `tool_specs()` 即可。
- **回放环境**：
  - Jev-as-IF 调用了标准轨迹以外的参数时，结果会是 `approx` 或 `miss`；
  - 工具几乎不耗时，所以耗时主要反映大模型和 Jev。
- **执行器还没做的优化**：
  - 循环里的工具调用是串行的，论文里的并行化和降为运行时流程还没实现；
  - 每个原语单独发请求，论文里同一轮原语的批处理还没实现；`jev.choice(k="*")` 和 `jev.filter` 内部已经是一次请求问完所有候选。
- **"选择型绑定"的统计**以本文件夹的 `finmcp.screen()` 为准。
