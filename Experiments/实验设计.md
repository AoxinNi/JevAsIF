# 实验设计：Jev-as-IF —— 基于图的工具编译器

> 版本：2026-10-07 第三版，取代前两版。对应论文草稿 [Texpaper/](../Texpaper/) 第 6 节。
> 全文截止 2026-10-25（摘要 10-18），今天起 18 天。

---

## 0. 一页结论

**论文主线**：Jev-as-IF 是一个**基于图的工具编译器**。agent 根据图提供的信息，一次写出受限 Python 子集（PyIF）的代码；编译器对照图做检查、优化，并降为可执行流程；运行时由执行器调用工具，由 Jev 判断代码里的语义条件（`jev.choice`、`jev.noul`、`jev.filter`）。整条工具链一次跑完，只有在 Jev 没把握时才回到大模型。

**编译器的两个关键设计，也是所有消融实验的两条轴：**

| 设计 | 在编译器里的角色 | 要证明什么 |
| --- | --- | --- |
| **图引导（SOG，对象和操作分开建图）** | 编译器的输入和类型系统：操作图提供类型化的接口桩和数据流检查；对象图为 Jev 的判断提供语义 | ① 比平铺工具定义、只有工具依赖图、只有知识图谱、合成一张图都好；② 工具越多，上下文越稳定；③ 能半自动建出来 |
| **Jev-as-IF（在代码里调用 System-1 原语）** | 代码里语义条件的运行时求值方式 | ① 比"回到大模型""重新规划""用代码规则硬判断"省调用且不掉准确率；② 收益来自编译这个架构，不只是 Jev 这个模型；③ 用对象图构造问题、批处理、门控各自都有用 |

**主要对手从 ReAct 换成写代码的 agent（PTC）**：2×2 析因实验以 PTC 为基线，衡量"加图"和"加 Jev"各自的作用和交互。ReAct、ReWOO、LLMCompiler 保留在主表里作参照。

**关于"准"**：主张是**总体成功率不下降**，同时 3 类错误明显减少：

- 调错接口：由静态检查拦住；
- 选错实体：由对象图语义减少；
- 编造参数：由溯源检查拦住。

所以主结果外加一张错误类型表。

**数据筛选**：选择型绑定的统计只用来切分子集（"含语义判断"和"只有机械依赖"）和提供门控标定集，不作为研究问题。

**可行性**：P0 约 19 人日，再加 4 天写作。两个人勉强可以，一个人做不完。

## 4. RQ2：图引导的消融

原则：所有表示形式都**从同一份人工整理的源数据渲染成接口桩**，只改变 agent 看到的结构和编译器能做的检查。默认使用完整的 Jev-as-IF 编译器。

### A1 表示形式（核心，P0，249 条）

| 变体 | 渲染出的接口桩 | 编译器能做什么 | 预期 |
| --- | --- | --- | --- |
| 平铺工具定义 | 函数只有入参，返回值没有类型 | 不能检查字段；判断原语只能看到原始值 | 字段靠猜，首次通过率低 |
| 只有操作图 | 返回值有类型，有派生的数据流 | 能检查数据流；但判断时缺少实体的标签、含义和规则 | 能通过检查，但判断准确率下降 |
| 只有对象图 | 实体类型和说明齐全；操作列在实体下面，没有输出类型和数据流 | 不能检查数据流 | 依赖靠 agent 自己推断，代码出错多 |
| 合成一张图 | 概念关系和数据流混在同一张图，按相同跳数披露 | 能检查，但上下文更大 | 提示词变长；可能把关系误读成调用顺序 |
| **SOG** | 分体结构 | 全部检查和完整的问题构造 | 各项都最好 |

### A2 关掉静态检查（P0）

SOG 不变，只是编译器不做检查，代码直接运行，出错再处理。指标：调错接口和编造参数的错误数、运行时失败数、修正轮数。**这是"准"的直接证据。**

### A3 披露方式与 A4 工具数量扩展（P0，合成环境）

- **披露方式**：按对象范围披露（h = 0 / 1 / 2）、全部披露、按工具检索 top-k。
- **工具数量**：51、100、200、500。
- **指标**：提示词 token、成功率、额外查询次数。

**这是图引导最直观的一张图**：工具越多，SOG 的上下文越平稳。

### A5 建图方式（P0）

比较自动建图（论文 §3.4 第 1 到 5 步）和人工整理两种 SOG。指标：

- 成功率；
- **派生边对轨迹依赖的召回率**；
- 人工整理用了多少人时。

## 5. RQ3：Jev-as-IF 的消融

默认表示形式固定为 SOG。在"含语义判断"子集（149 条）上报告。

### B1 语义判断怎么执行（核心，P0）

| 变体 | 代码遇到语义判断时 | 说明 |
| --- | --- | --- |
| 没有原语，回大模型 | agent 把数据交回大模型再判断（PTC 的自然做法） | 衡量原语省掉了多少轮调用 |
| 没有原语，只能用代码规则 | 禁止回大模型，只能写字符串匹配、关键词规则 | 证明需要语义判断，规则太脆弱 |
| 遇到判断就重新规划 | 把已有结果交给大模型，重写剩下的代码（LLMCompiler 式） | 证明"把判断写进代码"优于"遇到再重写" |
| 原语改由大模型判断 | 代码完全相同，`jev.*` 换成大模型 | **关键对照**：分离"编译带来的收益"和"Jev 这个模型带来的收益" |
| 原语改由开源模型判断 | 代码完全相同，换成开源重排模型 | 证明收益不依赖闭源的 Jev |
| **原语由 Jev 判断（本方法）** | | |

### B2 判断后端（P0，离线，最先做）

在约 540 道判断题上，比较 Jev、开源重排模型、小型生成模型（可选）、大模型的准确率、ECE、AUROC、延迟和每千次判断的成本。按候选数分桶；名称近似的难例单独报告。花费不到 1 美元。

### B3 用对象图构造问题（核心，P0，连接两个设计）

| 变体 | Jev 看到的内容 |
| --- | --- |
| 只有原始值 | 候选编码和 agent 写的一句问题 |
| 加上标签 | 编码和它在对象图里的标签属性 |
| **完整构造** | 标签 + 相关属性的含义 + 实体规则（作为判断边界）+ 裁剪后的状态 |

### B4 门控（P0）

- **门控方式**：不设门控、固定阈值（0.8）、共形门控。
- **α 扫描**：α ∈ {0.01, 0.02, 0.05, 0.1, 0.2}，先在离线判断题上算，再在端到端实验上抽两个 α 值验证。
- **回退方式**：一次大模型修正、直接问用户、中止。

### B5 批处理、B6 顺序去偏（P1）

- 批处理：同一轮里状态相同的原语合并成一个请求，对比逐个请求。
- 顺序去偏：r = 1 或 3 次循环置换。

### 按原语类型拆分（P0，不需要额外运行）

把 B1 和 B3 的结果按 `choice`（选一个）、`choice`（选多个）、`noul` 条件分支、`filter` 分开报告。
